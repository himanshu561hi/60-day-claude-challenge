Module 1

The Foundation: Beyond HTTP

Traditional web communication is built on HTTP, a stateless, half-duplex protocol. The client asks, the server answers. If the client wants new data, it has to ask again.

Analogy: HTTP is like sending a physical letter. You mail it, wait days for a response, and repeat. WebSockets are like a phone call. Once the connection is established, both parties can speak and listen simultaneously.

The Problem: Polling

Before WebSockets, developers faked real-time updates using Polling (asking the server every X seconds) or Long-Polling (server holds the request open until data is ready). Both are resource-intensive.

Enter WebSockets (ws://)

WebSockets begin as a standard HTTP request but include an Upgrade: websocket header. If the server agrees, the connection is "upgraded", the HTTP handshake is completed, and a persistent, bidirectional TCP connection is kept open.

The WebSocket API

The native browser API for WebSockets is incredibly simple. It revolves around four main events and two methods.

// 1. Establish connection (ws:// or wss:// for secure)
const socket = new WebSocket('wss://echo.websocket.org');

// 2. Listen for connection open
socket.onopen = function(event) {
    console.log('Connected!');
    socket.send('Hello Server!'); // The send method
};

// 3. Listen for incoming messages
socket.onmessage = function(event) {
    console.log('Received:', event.data);
};

// 4. Handle closure & errors
socket.onclose = (e) => console.log('Closed');
socket.onerror = (e) => console.error('Error', e);
Common Misconception: WebSockets are automatically reconnected if they drop.
Truth: They do NOT auto-reconnect. The native API drops the connection on network failure, and you must write logic to instantiate a new WebSocket() to reconnect.

Module 3

Advanced Concepts & Robustness

A simple new WebSocket() is fine for demos, but production requires handling reality: dropped WiFi, silent disconnects, and complex data.

1. Heartbeats (Ping/Pong)

Sometimes, a connection drops silently (e.g., losing cellular signal) without triggering onclose. To detect this, we use Heartbeats: the client periodically sends a "ping" message, and the server replies with a "pong". If no pong is received within a timeout, the client manually closes and reconnects.

2. Data Framing (JSON vs Binary)

WebSockets can transmit Strings, Blob, or ArrayBuffer. Most apps stringify JSON objects to send complex data structures with "types".

// Standard pattern for sending structured actions
const payload = {
    type: 'JOIN_ROOM',
    room_id: 'gaming_lobby',
    user: 'Player1'
};
socket.send(JSON.stringify(payload));

3. Exponential Backoff

When implementing auto-reconnect, don't spam the server. If the server is down, 10,000 clients instantly retrying every 1 second will DDoS your own backend. Use Exponential Backoff: wait 1s, then 2s, then 4s, 8s, etc.

Module 4

Architecting Real-time Apps

Scaling WebSockets introduces statefulness to your backend. In standard HTTP, a load balancer can route request 1 to Server A, and request 2 to Server B. With WebSockets, the user is permanently bound to Server A.

The Pub/Sub Problem

If Alice is connected to Server A, and Bob is connected to Server B, how does Alice's chat message reach Bob?

Solution: Redis Pub/Sub
WebSocket servers use a centralized message broker (like Redis). Server A publishes Alice's message to a Redis "Channel". Server B is subscribed to that channel, receives the message, and forwards it to Bob.

Rooms and Channels

Rather than broadcasting to everyone, payloads include routing information. The server maintains in-memory Maps correlating connection IDs to Room IDs.
